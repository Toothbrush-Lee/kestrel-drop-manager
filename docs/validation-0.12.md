# 0.12 可靠性与性能验证

日期：2026-10-28。版本 0.12.0，SQLite schema 4。重点是有界完整校验、恢复后的运行模式、损坏检查、已提交结果语义和取消清理。

## 改动与保持的约束

正式记录以 1,000 条为一批读取，逐条解码并与原始字节比对；pending 仍逐块验证摘要、序号、布局和跨会话游标。未引入 quick 检查替代备份完整检查，不改变提交后 ACK 顺序。升级用具名 schema 对象和分批更新，保持升级前快照及事务回滚。

schema 2/3 旧快照按原对象集读取，schema 4 缺审计表或视图会报错；检查同时验证列定义、主键、显式索引键和视图列，不声称证明全部 SQL 约束或自定义触发器正确。恢复产物仍为 DELETE 单文件，作为运行库写入初始化时核验结构并启用 WAL；只读不切换模式。

首次重试只统计当前尝试的 pending，旧尝试单列为 superseded_records；resumable_records 对首次下载为零。保留旧块直到成功发布，不自动删除异常证据。完整检查仍覆盖旧块摘要。

最终 ACK 失败只在完成回调已成功返回后形成明确提醒。管理器显示 saved_warning/退出码 0，正式数据仍可用，批量重试排除该台。写块/完成事务失败继续失败，取消继续返回 130；没有调整设备序号规则。

## 离线测试

310 项测试通过；增加以下行为检查：

- 2 万条全量检查的 Python 分配峰值小于 12 MiB，并检测最后一条损坏，拒绝发布无效备份并清理临时文件。
- 恢复后只读检查不变更文件；写入初始化启用 WAL，读快照保持稳定的同时可完成另一写事务；源备份不变，后续备份仍单文件。
- 删除 schema 4 表/索引/视图、改变列或索引键会被拒绝；旧 schema 3 快照仍只读通过。现有 schema 2 升级测试同时核对 WAL。
- 首次重试的当前/旧尝试/可续传数量分别正确，旧尝试损坏仍被发现，成功后清理。
- 最终 ACK 错误经真实管理器事件→worker 校验→TUI 显示，不冒充 pending、不重复入库、不进入批量失败重试。
- 真实 worker 子进程运行 CLI，模拟 GATT 在块提交后等待；发送真实 SIGINT，确认停止通知、退出 130、关闭管道，并能从数据库检查到 durable pending。
- Python 3.11 云端及本地复现：wait_for 在内部 I/O 完成与外部取消同时发生时可能吞掉取消。协议及 GATT 设置收发改用 asyncio.timeout 的直接等待作用域，并以确定性竞争测试覆盖两种操作；真实 SIGINT 测试保持不放宽。
- 修正的并发取消用例另行重复 100 次，0 次失败。模拟客户端进入连接的等待使用 Event 并清理未完成的进入过程。

基础 Ruff 规则只阻止语法、未定义名称和部分明显控制流错误；不是全库格式化或完整类型检查。普通启动不安装 lint 依赖。CI 的 Linux 单元矩阵加入实际发布使用的 Python 3.13。

## 规模实测

本机 Python 3.14.3 / SQLite 3.50.4 / macOS ARM64。合成 D3 记录重复合法时间，适用于校验、布局和内存测量，不能代表 BLE 吞吐或日期筛选。内存为 tracemalloc 的 Python 分配峰值，不是 RSS，也不包含生成夹具的内存。耗时单独在不开启 tracemalloc 时测量，各一轮，不能当作稳定的 p95。

| 分布 | 完整检查耗时 | Python 分配峰值 |
| --- | ---: | ---: |
| 1 台 × 100000 条 | 0.43 s | 0.670 MiB |
| 100 台 × 1000 条 | 0.43 s | 0.349 MiB |
| 1 台 × 1000000 条 | 4.34 s | 0.670 MiB |
| 100 台 × 10000 条 | 4.40 s | 0.685 MiB |

同机本轮修改前，1 台 10 万条约 184.39 MiB，100 台各 1,000 条约 1.65 MiB。因此原问题主要随最大历史段增长，不能把分散在百台的百万条直接外推成单设备百万条的峰值。新实现主要随读取批次、设备摘要和单块大小增长；异常巨大 BLOB 仍需读取该块，不承诺任意损坏文件均低于固定内存值。

复现：

```sh
uv run --locked python -B tests/run.py -q
uv run --locked --group lint ruff check .
uv run --locked python -B scripts/check_benchmark.py --records 100000 1000000 --output /tmp/kestrel-check-new.json
```

基准输出已有时拒绝覆盖，临时数据库完成后清理。原始 JSON 保存在本地 data/analysis/hardening-0.12-20261028/，不进入 Git。

## 验证边界

没有连接、校时或修改真实设备。保留官方生命周期递增序号规则，没有按 count(0) 与绝对游标的差值推断复位；没有新建历史代、删除证据或降低持久化强度。旧 CSV 诊断保留旧方言及对应测试，原生会话强制显式型号；不把这次命名隔离当成旧方言已经获得官方协议验证。

原生分发继续使用 GitHub Actions 的 macOS ARM/Intel、Linux x86_64 构建和 PTY 冒烟；实际硬件、固件兼容和蓝牙吞吐仍需现场验证。新增 Web、服务化、网络共享活动数据库均不在本轮范围。
