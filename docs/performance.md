# 0.10 性能分析与优化顺序

本文保留原始分析；上述优化已在 [0.11 验收与性能对比](validation-0.11.md)中落实，当前行为以最新记录为准。

分析日期：2026-10-27，代码基线 0.10.0。本轮完成代码审查、隔离基准和 cProfile 分析，尚未修改业务行为。原始结果在本地 `data/analysis/performance-0.10-20261027/benchmark.json`，复现工具为 [scripts/performance.py](../scripts/performance.py)。

当前四台、约 3.6 万条记录的档案，本地查询很快，等待主要在扫描和蓝牙操作；扩展到百台后，重复读取整个设备库和反复解码其他设备的暂存记录值得优先处理。SQLite 目前能够承担此规模，不需要因此更换数据库或增加一份运行 CSV。

## 测量方法与边界

- 本机 Python 3.14.3、SQLite 3.50.4、macOS 27.0.1 ARM64。结果反映本机当前环境，不能代替其他电脑和蓝牙适配器的实测。
- 真实档案通过只读 SQLite 连接复制到临时目录，再对副本测量。快照中有 4 台、35,661 条正式记录；这是测量时的副本，不是对以后条数的承诺。复制前后原主库 SHA-256 相同。
- 另外生成 4×10,000、100×1,000、100×10,000 条 D3 合成档案，最大约 150 MiB；结束后删除临时数据库与测试 CSV。合成观测使用重复的合法时间和原始字节，适合测计数、物化和布局开销，不能用于推断日期筛选的真实选择率。
- 每项先预热，通常采样 5 次，批次遍历/子进程/导出等采样 3 次，界面采样 10–20 次。表中为未开启 profiler 的中位墙钟时间；JSON 保留逐次样本、最大值和 CPU 时间。不把少量样本包装成可靠的 p95/p99。
- TUI 使用空屏幕模型，包含 Python 排版和页面绘制调用，不包含真实终端渲染与 I/O。内存是 tracemalloc 统计的 Python 分配峰值，不是整个进程 RSS。
- 所有测试不连接 BLE、不校时、不修改配置。本次没有测得真实蓝牙吞吐、射频拥塞或端到端下载提速比例；不能把本地处理速度当作设备下载速度。子进程指标的墙钟包括启动和业务执行，CPU 计时仅来自父进程。

复现方式，在项目目录运行：

```bash
uv run --locked python -B scripts/performance.py --output /tmp/kestrel-performance.json
# 可选：只读复制实际数据库后测量该副本
uv run --locked python -B scripts/performance.py --snapshot archive/library.sqlite --output /tmp/kestrel-performance-with-snapshot.json
```

已有输出文件会拒绝覆盖；`--small` 跳过百万条正式记录场景。一次测试会临时生成约数百 MiB 的资料，基准完成自动清理。长期保留的结果放在 `data/analysis/主题-日期/`，不要放在根目录。

## 测量结果

| 操作，中位时间 | 当前档案副本：4 台 / 35,661 条 | 合成：100 台 / 100,000 条 | 合成：100 台 / 1,000,000 条 |
| --- | ---: | ---: | ---: |
| 整个设备库状态 | 0.58 ms | 2.05 ms | 15.80 ms |
| 单设备摘要 | 0.27 ms | 0.24 ms | 0.38 ms |
| 一台完成后的结果整理 | 0.60 ms | 2.00 ms | 15.86 ms |
| 对所有设备依次整理完成结果 | 2.81 ms | 196.00 ms | 1,524.72 ms |
| 查看最近 100 条 | 0.82 ms | 0.87 ms | 1.20 ms |
| 单设备完整导出 | 49.90 ms | 5.44 ms | 45.15 ms |
| 新进程执行一次 list | 45.47 ms | 46.92 ms | 61.02 ms |

导出规模与该设备自身条数有关：快照第一台约 1.4 万条，两个百台场景分别每台 1,000 / 10,000 条，不能仅按全库大小横向比较导出耗时。

| 额外场景 | 中位耗时 |
| --- | ---: |
| 100 台列表，单次 Python 绘制 | 0.10 ms |
| 日志 500 条，每条 100 字符，单次绘制 | 5.20 ms |
| 日志 500 条，每条 1,000 字符，单次绘制 | 44.49 ms |
| 100 台库，2 台各有 10,000 条待确认，另一台整理完成结果 | 33.96 ms |
| 100 台库，8 台各有 10,000 条待确认，另一台整理完成结果 | 122.35 ms |

上述暂存场景使用 100 台 / 100,000 条正式记录的合成库。额外模拟没有实际建立 8 条蓝牙连接，只建立了 8 份合法暂存数据，因此不能据此声称 8 台硬件并发已经验证。

独立持久化测试中，2,000 条记录分成 40 块、每块 50 条：每块校验并完整提交中位约 0.75 ms，40 次合计约 30.6 ms，最终校验和发布约 17.5 ms。该数据包含本机 SQLite FULL 提交开销，不代表所有硬盘、电源故障和文件系统条件，也不是 BLE 吞吐率。

## 第一优先级：减少整批开始前的额外等待

当前 `manager.py` 的多台下载在真正连接前调用一次 `scan_snapshot(args.timeout)`；默认下载 timeout 为 20 秒，所以即使刚在 TUI 完成 15 秒扫描，按多选下载还会执行完整的 20 秒广播收集（取消或错误除外）。这个等待远大于当前档案的本地数据库处理。

优化方向是保留用户要求的 15 秒标准扫描，同时让后续多台定位在**全部明确地址都已找到时提前结束**。这不是恢复 5 秒快扫，也不因看到第一台就丢弃其他目标。

实施时应保持：

1. 已知地址只用于定位，连接后仍核验真实序列号和型号。
2. 存在只有编号的目标时，继续完整窗口以检查重复广播身份，不能盲选第一个编号匹配。
3. 地址失效、漏扫或重复编号时保留明确失败与回退规则。
4. 不同时扫描和传输来换取未经验证的提速，避免干扰其他连接。

这里是源码确定存在的固定等待，实际可节省多少取决于目标广播到达时间，需要下一轮实机阶段计时验证。标准扫描本身不建议再次缩短。

## 第二优先级：完成结果只查询当前设备

`Library.complete_download()` 目前调用整个 `Library.status()`，然后在返回列表中寻找一台设备。`Store.status()` 对每个历史段计数，并通过 `_pending()` 校验和解码所有待确认块。零新增判断中也存在调用全库 status 的路径。

无暂存时，百万条合成库的一台结果整理约 15.9 ms，遍历百台约 1.52 秒。cProfile 显示一次完成整理会执行约 204 次 SQLite execute；多数时间在数据库查询。存在 8×10,000 条暂存时，仅整理另一台的结果也约需 122 ms。

这些同步查询运行在下载的 asyncio 事件循环中，执行期间会推迟其他连接任务被调度。因此，改善范围比“结果页稍快一点”更广；但本轮没有实测由此导致的 BLE 超时或吞吐损失，不能把它当作已发生的故障。

建议给 `Store.status()` 增加可选 serial 条件，完成整理和零新增判断限定到当前设备，保留现有输出和该设备所有恢复边界校验；列表刷新仍查询全部。单设备摘要约 0.38 ms 只说明限定范围的潜力，摘要没有相同的暂存校验，**不是优化后等价接口的成绩**。

验收应检查：结果字段一致、并发设备错误隔离、首次/增量待确认状态一致；一台完成时不再解码其他设备的暂存。先做查询范围优化，无需增加冗余条数缓存或调整 schema。

## 第三优先级：日志缓存与按需重绘

TUI 使用 100 ms 输入等待，循环每轮都调用 draw；日志页每次 draw 都把完整文本重新折行，随后只展示其中一屏。500×1,000 字符时单帧约 44.5 ms，cProfile 的主要热点是 wrap_lines 和 Unicode 宽度处理。Profiler 本身有明显开销，文中使用未开启 profiler 的 44.5 ms，而非 profile 输出中的累计耗时。

建议：

- 打开文本或文本内容/窗口宽度变化时折行一次，滚动与普通重绘复用结果；resize 必须使缓存失效。
- 没有输入、没有可见状态更新、没有窗口变化时不重新绘制。任务进度和动画按限制频率刷新，取消仍及时处理。
- 只绘制当前可见顶层页面，避免先绘制列表再立即用不透明页面覆盖。

当前百台列表绘制只有约 0.10 ms，本身没有明显问题。优先处理长日志的重复工作，验收重点是滚动、日志重新打开、窗口变窄/变宽、表单光标和后台取消不退化。

## 后续：批量设置减少重复读取

批量配置正确地按设备隔离身份、旧值与审计。当前每台配置前后各执行一次完整 inspect；校时还在写入流程内做一次时钟回读。以校时为例，当前会读取初始时钟、写后核对时钟，并在最终完整 inspect 中再次读取时钟；固件、硬件版本等稳定字段也重复读取。

后续可在**同一次连接内**复用稳定字段，仅重新读取与变更及审计有关的动态值；保留真实身份读取、请求字段回读、设置保留字节核对，以及实际写入时的电脑时间。不把前一台的旧值或时间复制给下一台。

这部分必须新增每阶段的连接/GATT/读旧值/写入/回读/审计耗时，再做实机前后比较。目前没有足够证据量化收益；不建议先把批量校时改成 8 台并发或并发发送同一设备的 GATT 命令。

## 后续：导出改为分批读取

`Store.query()` 当前先 fetchall，再把每条 sqlite3.Row 转成 Python 字典；`Library.export()` 把这个完整列表交给 CSV writer。每台 10,000 条时，仅完整查询物化峰值约 10.2 MiB，当前快照第一台约 12.6 MiB。日常最近 100 条查询仍约 1 ms，目前没有导出小数据的紧迫问题。

历史持续积累后，可用 fetchmany/迭代器按批输出 CSV，保持查询快照、设备顺序、日期边界、临时文件与原子发布、不覆盖已有文件，以及取消时关闭连接并清理临时文件。需要实际测峰值内存；不能从本轮数据直接宣称已解决百万条单设备导出。

## 保留的可靠性边界与实施顺序

本机每块持久化中位不到 1 ms，没有证据支持通过减少落盘来提速。保持 CRC、原始记录一致性、事务完整性、FULL 同步、持久化后 ACK、完成确认和恢复边界校验，完整检查及备份验证继续执行。

建议先实施“批量目标全部发现即结束定位”和“完成时只查询本设备”，再做日志缓存/按需重绘；之后基于阶段计时考虑配置读取与流式导出。每一步单独测量与回归，比较相同设备数、条数、暂存量和蓝牙条件下的端到端耗时，不把局部查询的倍数当作整个软件提速倍数。
