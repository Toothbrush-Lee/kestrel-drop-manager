# 存储设计：schema 5 / 0.14.0

SQLite 是运行时唯一权威来源。CSV 仅作导出或旧档案导入；旧格式恢复代码只在迁移副本及底层诊断工具中使用。

## 持久化内容

| 表 | 内容 |
| --- | --- |
| devices | 序列号、型号、预留用户名称 |
| histories | 所属设备、历史段编号、正式起止游标；未完成首次下载时游标为空 |
| transfers | 请求游标、查询数量、解析器版本、开始与结束时间、会话状态及完成验证摘要 |
| pending_blocks | 每会话从零连续的块序号、原始记录载荷和 SHA-256 |
| observations | 历史段与绝对位置、原始记录、解析字段及接收块位置 |
| device_actions | 配置请求、前后状态、开始/完成时间和明确结果；不把实时采样混入历史 |

正式记录主键为 `(history_id, absolute_cursor)`；历史段由 `(serial, generation)` 唯一标识。时间相同的观测不会合并。D1 / D2 / D3 分别使用 9 / 16 / 21 字节记录，解析版本为 `d1-9-v2` / `d2-16-v2` / `d3-21-v2`。先核对型号和字段声明，再按对应长度解码；原始载荷长度、字段值、解析器版本必须与该历史段设备型号一致。D1/D2 缺少的测量存 SQL NULL，不能用零替代。表结构预留多个历史段，但当前没有自动分段或手动接受设备重置的入口，遇到缺口必须停止。

`device_overview` 是只读关联视图，实时计算每台设备的记录数、首尾游标、按序号最新的记录时间和最近下载时间；不往 devices 重复写统计。`absolute_cursor` 为兼容旧库保留的零基位置，查询和导出另行计算官方设备序号 `device_sequence = absolute_cursor + 1`。

没有 `row_json`、永久 CSV、字段表头缓存、入库批次镜像或 CSV 路径。数量、时间范围来自查询。原始记录用于重新解码核验，解析列用于 SQL 筛选，二者的重复具有明确用途。

## 块接收与完成事务

连接前获取数据目录的操作系统排他锁，整个导入、批量下载、配置或迁移持有该锁，防止两个应用写入流程交错。锁作用于目录描述符，无需创建锁文件；进程结束由系统释放。SQLite 事务仍负责数据库内部原子性。日常查询使用 `mode=ro` 与 `query_only=ON`，不获取目录写锁。

收到数据块后，协议层验证 CRC、序号、块内记录和时间。数据库再核验原始字节、块位置及连续的设备序号。校时导致的合法时间变化不会破坏序号链，不按时间去重或改写历史。`BEGIN IMMEDIATE` 插入 pending_blocks，`synchronous=FULL` 持久化提交后才允许块 ACK。块数及已收记录数由块内容得到，不另外维护检查点 JSON。

每次重连创建新 transfer，接收块序号从零重新开始，设备记录序号继续增长。旧会话的待确认块保持原位；恢复时核验载荷摘要、会话请求游标和连续边界。已接收边界为正式游标加可信待确认记录数。

收到最终完成消息后，在完成 ACK **之前**执行事务：

1. 从数据库重读本会话块，与收到的记录逐项比较。
2. 验证查询数量下限、块连续性、时间字段合法性、合理新增数量、最终游标。
3. 核验跨会话累积的待确认记录，与正式游标连续。
4. 插入正式观测，更新 histories 的游标，完成关联会话，记录最终验证摘要。
5. 删除该历史段的待确认载荷，包括已被替代的首次下载暂存。
6. 提交成功后，向设备发送完成 ACK。

任何一步失败，正式记录、游标、会话完成状态、暂存清理一起回滚。数据库提交后 ACK 发送失败，已提交数据仍然有效，下次从新的正式游标查询，不重复插入。

首次请求游标零可能被设备解释为“最早仍保留的记录”，因此最终游标到达前不能推算绝对起点。首次中断的数据仍保存在库中，下次完整重读；只有成功发布后才删除被替代载荷。它们不会被当成正式观测，也不会生成猜测的绝对编号。

## 查询与检查

`list`、`status`、`records` 和 `export` 不读旧 CSV、不补入库、不更新时间。最新记录用主键排序和 LIMIT，时间筛选使用历史段与时间索引。状态统计由查询获得，待确认边界会解码核验，因此 pending 很多时刷新仍有与暂存大小成正比的工作量。

`db` 是显式完整检查，包含 SQLite integrity_check、外键、正式游标连续性、原始字节与解析字段一致性、时间字段合法性、待确认块摘要、会话边界、解析器版本及配置审计完成证据。日常预览不逐条重解码全部正式历史。

示例只读 SQL：

```sql
SELECT d.serial, h.generation, count(o.absolute_cursor) AS records,
       h.first_cursor, h.next_cursor
FROM devices d JOIN histories h USING(serial)
LEFT JOIN observations o ON o.history_id=h.id
GROUP BY h.id;

SELECT absolute_cursor, timestamp_device_local, temperature_c,
       relative_humidity_pct, station_pressure_hpa
FROM observations WHERE history_id=1
ORDER BY absolute_cursor DESC LIMIT 20;
```

设备时间没有时区；会话的 started_utc / finished_utc 是电脑记录的 UTC 时间，二者用途不同。导出增加 serial、history_generation、absolute_cursor 和计算出的 device_sequence，不包含未确认数据。

## 备份和恢复

备份通过 SQLite backup API 取得一致快照，目标使用 DELETE journal 模式形成可单独保存的文件。对目标运行完整检查、同步文件，再以独占原子链接发布，最后同步目录。不会覆盖已有文件，不扫描 CSV，不修改源库。

快照包括 pending_blocks、transfers 和 device_actions，可以在空目录恢复并继续增量同步。首次下载中断的快照恢复后仍需从零完整重读。导出、位置设置和 legacy 不在快照内。恢复先验证格式与业务约束，目标必须为空，不支持覆盖一个活动库。

## 旧版迁移

schema 2/3 → 4 在首次写入或显式 migrate 时进行：先用 SQLite backup API 保存独立、完整核验的旧版本快照；在一个事务内完成必要表结构升级，增加配置审计表和总览视图，从不变的原始记录重解码 24 位热指数，再更新解码版本。旧版快照以原 v1 语义只读核验，升级后的库使用 v2。任何 DDL、重新解码或索引写入失败都整体回滚；只读查询不触发升级。快照使用临时文件校验、fsync、独占原子链接发布。

schema 1 / CSV 旧档案迁移是显式操作。当前和旧版下载锁都要获得，避免旧程序同步时切换文件。

将旧文件复制到 legacy 内的迁移暂存目录，逐文件比对摘要；旧数据库通过 backup API 生成一致快照。CSV 的恢复、检查点尾部截断和完成日志恢复只在工作副本上执行。若数据库和 CSV 同时存在，旧数据库必须与 CSV 前缀在游标及原始记录上逐条一致，解析字段也必须与原始字节一致。数据库少于 CSV 的已确认尾部允许补入；数据库较长或内容冲突拒绝切换。

可信的增量 pending 按原会话及块顺序迁移；没有连续块检查点的非空旧 pending 拒绝猜测恢复。已完成但尚未发布的首次下载，可用原始元数据在副本上核验后迁移；首次未知游标的 partial 仅冻结保存。

新库完整检查后，先持久化旧材料和清单目录。旧库切换前必须完成 WAL checkpoint 并取得 DELETE 模式，不能直接替换仍有活动 WAL 的主文件。新库文件原子替换后同步数据目录，才清理与冻结副本摘要一致的旧运行文件。迁移清单和库中迁移 ID 关联，清理可重试；外部修改过的源文件会保留并报告。失败迁移的暂存材料保留用于排查，不自动删除未知证据。

迁移成功的 legacy 文件设为只读，但它们仍需单独备份。迁移不会改动项目 data/originals 下的历史原件。

## 0.12 的检查与恢复边界

完整检查保持逐条原始字节重解码、测量值比对、正式游标连续性、待确认摘要与序号、外键和 SQLite 完整性校验；正式记录按 1,000 条一批读取，不建立整段副本。待确认块按块验证，状态查询仍校验恢复边界，不用未经校验的缓存计数代替。单个异常巨大 BLOB 仍需读取该块，峰值不是对任意损坏文件的固定承诺。

检查按 user_version 验证必需的表、列定义、主键和显式索引键、视图列；schema 2 允许原有 D3 测量列非空约束，schema 2/3 不要求后来新增的审计表和视图。该检查不声称验证任意自定义触发器或所有 SQL 约束的语义等价性。

备份与恢复产物继续为 DELETE 模式单文件；只读查看不修改它。作为运行库打开（Store(create=True)）时，在结构核验后检查并启用 WAL，失败会明确报错。db 输出 journal_mode；不能仅以连接关闭后是否还存在 -wal 文件判断模式。活动库仍建议放在本地文件系统，导出及完整备份再用于共享。

status 的 pending_records 是当前 receiving/interrupted 尝试的记录数；superseded_records 是首次重试保留的旧尝试证据。resumable_records 只表示增量恢复可复用的记录数，首次下载恒为 0，必须从零重新请求。旧证据仍参与完整检查，成功发布当前完整历史后才一并清理，不提前删除。

已完成事务后最终 ACK 发送失败，结果为 saved_warning（退出码 0），附 completion_ack_failed 提醒；此时正式记录、游标和校验都已提交，不属于 pending，也不自动重复下载。块写入或完成事务失败仍按原路径失败，不能借此状态绕过校验。取消不转换为成功。

## schema 5 本地设备资料

`devices.management_code` 是可选且非空值唯一的管理编号，`participant_code` 是可选的当前受试者代号（非唯一，允许同一人多台设备）。两者都是 TEXT，空字符串表示未编号/未分配；序列号仍为主键，alias仍为原有别名。`device_overview` 展示新字段。

资料更新与 `device_actions` 审计在同一个事务中完成，`requested.local_metadata` 区分本地资料操作与设备配置。before/after保存旧新值，UTC记录操作时刻；同值不新增审计。它记录登记操作时间，不能代替实际佩戴或观测时段。不会在observations上重复存代号，也不按当前devices关联改写旧数据。

4→5首次写入前创建 `backups/schema4-before-upgrade-*.sqlite` 独立备份，完整检查后，在一个事务中添加列、部分唯一索引与更新视图。DDL失败不留下半套字段。2/3先按历史流程到4（保存原版本备份），再完成资料升级。只读兼容2/3/4/5，旧版程序无法打开5。
